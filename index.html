      Choosing issues and talking to maintainers

      Pick issues that show you can solve real problems, and ask good questions in public.

      How to choose an issue

      1. Prefer a bug you can reproduce on your laptop over a documentation typo. It proves you can find and fix a real problem.
      2. Add a test with your fix. It says much more about you than a typo fix.
      3. After 2 or 3 merges, move closer to a likely 2027 project idea. That work becomes the base of your proposal.

      Do and don’t

      Do

      • Ask in the project’s public chat, or on your issue or pull request
      • Read the code first, then ask one clear question
      • Talk to the people who review recent pull requests
      • Link every pull request, merged or not, in your proposal

      Don’t

      • Send private messages to maintainers
      • Write “please guide me” or “how do I get started?”
      • Only message the most famous maintainer
      • Write a proposal with no work behind it

      Find who reviews code

      Open the last 20 merged pull requests and see who reviewed them. From February, the mentors named on each project idea are good people to talk to too. This command lists the most active reviewers. It needs the GitHub CLI (gh); change the repo name.

      gh pr list -R zulip/zulip -s merged -L 30 --json reviews --jq '.[].reviews[].author.login' | sort | uniq -c | sort -rn

      A question that works

      I’m working on #1234 (link). In module/foo.py, bar() is called from both X and Y, but only X resets the cache. Is that intentional, or should Y do the same? I traced it as far as baz() and wasn’t sure.

      It works because it names the issue, shows what you already checked, and asks one thing a maintainer can answer quickly.
